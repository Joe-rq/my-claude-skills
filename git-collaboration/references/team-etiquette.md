# 团队协作礼仪

## PR 规范

### PR 大小

```
✅ 推荐：200-400 行改动
⚠️ 最大：800 行（超过时拆分）
❌ 避免：> 1000 行（难以 review）
```

### PR 描述模板

```markdown
## 改了什么
- [ ] 改动 1
- [ ] 改动 2

## 为什么
解释背景、业务需求、技术原因

## 如何验证
- [ ] 测试步骤 1
- [ ] 测试步骤 2

## 关联
Closes #123
Depends on #456
```

### PR 生命周期

```
创建 → 开发 → PR → Review → 合并 → 删除

最佳实践：
- 开发完成后 24 小时内发起 PR
- PR 发起后 48 小时内完成 Review
- 合并后立即删除本地和远程分支
```

## Code Review 礼仪

### Review 者

- ✅ **及时响应**（24 小时内）
- ✅ **先肯定优点**，再提改进建议
- ✅ **区分"必须改"和"建议改"**
- ❌ 不要只批评不提具体建议
- ❌ 不要 blocking 小问题（格式、风格等）

### 被 Review 者

- ✅ **虚心接受**，不要 defensive
- ✅ **回复每一条 comment**
- ✅ **感谢 review 者**
- ❌ 不要 defensive
- ❌ 不要无视 comment

## 沟通规范

- ✅ **遇到冲突先问**（不要盲目操作）
- ✅ **PR 描述写清楚**（降低 review 成本）
- ✅ **复杂改动提前沟通**
- ❌ 不要直接 push main
- ❌ 不要 rebase 别人的分支
- ❌ 不要一个人闷头开发 1 周不沟通
